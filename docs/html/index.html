This project is designed to support the designing, editing and production of screens. There are 3 main sections: Networking, The database and The UI.

Getting started

To work on this project, first install Visual Studio Installer from here, install visual studio, and the "Desktop development with C++" workload. Then, make a directory called libraries. Create an account with Qt, and download the Qt installer. Go through the setup process, and select the components "Qt Design Studio 4.5.1", "Qt 6.7.2", "CMake 3.29.3", "Ninja 1.12.0". Set the download directory to in the libraries directory. Find the rest of the dependencies at T:/IT/Libraries.zip.

Network

The network follows a client server model. The server reads from the database when it starts up, and whenever a change is made to the database it rereads it and broadcasts the updated tables. The protocol for adding something new to the network is as follows:

COMPONENT INSERT

A request is made as a ComponentInsert by attaching a new object (such as MaterialPriceData) to ComponentInsert (CopmonentInsert::{...Data}) ComponentInsert is serialised. The serialisation definition for each component is inside the serialise method (might change).Size is determined by ComponentInsert::{insertName}serialisedSize() method. Buffer sent across network to server as a ADD_NEW_COMPONENT. ComponentInsert is then deserialised, each individual deserialise is in the ComponentInsert::deserialise(void*&& data) method, which replies upon an InsertType and an deserialise implementation in the method. DatabaseManager::insertComponent is called with the insert, which uses ComponentInsert::toSQLQueryString() to get the sql query. Database gets query, and status is returned. Also, the server checks what table was changed, fetches it from the database and broadcasts the new source data to all clients.

FETCHING

fetching starts with a RequestType being sent to the server. The server collects the data using DatabaseRequestHandler::{Name}Data, and pipes result into createSourceData, tempalted on the type of data being requiested (i.e. apertureData). constructDataElements<T> is then called, populating the given vector<T> and adding up the size. The reuqest type is added to the start of the buffer. serialiseDataElement<T> is ran on each element to put them into the buffer. The buffer is then given to DrawingComponentManager<T>::sourceComponentTable, which clears its components and recreates them from the provided data, through T::fromSource on the server side. The server sends over the raw source data and size to the client, where sourceComponentTable is ran to populate the clients DrawingComponentManager aswell.

Database

The database mainly revovles around an object DrawingComponentManager<typename T>, where T must inherit from DrawingComponent. This is a static class that stores all DrawingComponent's, can be used to get and update DrawingComponent's from anywhere, and is what the server updates when required. DrawingComponent's use two different ways of storing/access, handles and component IDs. Component ID's are the relevant components id in the database, meaning for any update to the database, these should be used. However, these ID's are not garunteed to be unique, and the IDs are not complete sequence, meaning that an ID of $n$ does not imply $n-1$ is also an ID. Handles are assigned by the drawing incrementally, meaning that handles are complete sequences. They are also garunteed to be unique. component manager successively, so that if $n$ is a valid ID, $n-1$ is also a valid ID and so on.

UI

The UI uses Qt and is mainly self explanitory. The only special case is the addons,AreaGraphicsItem<T, Us...> andGroupGraphicsItem<T, Us...>. Both of these are generic graphcs item to draw either a rectangle or a set of items respectively.

Build Structure

The system relies upon a few libraries available online, and two custom made libraries. The first is the Encrypt library, linked with encrypt.lib . This is enough to compile database_manager_core.lib , a library containing the core components of the database. There second custom library is Pricing-Package, linked as a pricing_package.lib and a pricing_package.dll for runtime. This relies upon both encrypt.lib and database_manager_core.lib. With this, you can build the whole project. The pricing algorithms are updatable without recompiling the main project, as long as the header is not changed, and no new data is required.

The core of the management of data is the DrawingComponentManager. As a result, both the main execute and the pricing_package.dll rely upon it. This creates an issue with DrawingComponentManager as it is a static class. As a result, pricing_package is responsible for controling the DrawingComponentManager and all its templates. In this case, the main executable can be instructed to reference the DrawingComponentManager references in pricing_package.dll, instead of each of them creating their own copies. In the future, this should be changed so that DrawingComponentManager is a singleton instead of static, and then give only the dll the ability to create one, and force the executable to yield creation to the dll.
